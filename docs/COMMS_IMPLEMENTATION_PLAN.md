# Section 4 — Communications: Implementation Plan

**Owner:** Xian Hui (primary) · Jiaming (secondary)
**Report section:** 4 (`design_report/05_communications.md`)
**Target stack:** Python 3.10+, `asyncio`, single event loop per process
(3.10, not 3.11, because the Ultra96's PYNQ image ships Python 3.10.4 and the engine has to run there
— see §1 on venue client isolation. Nothing here needs 3.11.)

This is the build spec for the Communications subsystem. It is written to be handed directly to an
implementation pass — every format, field, constant, and behaviour that a coder would otherwise have to
guess at is pinned down here. Where a value is genuinely a tuning knob it is marked **[config]** and
belongs in `shared/config/*.yaml`, not in source.

---

## 1. What Comms owns

Comms is not a link layer. It is the spine of the system: every other subsystem talks only to Comms, and
Comms owns the authoritative game state. Concretely, you own:

1. **The binary wire protocol** between FireBeetle and laptop — *both* sides of the definition. Firmware
   implements the ESP32 end, but the format, the C header, and the golden test vectors are yours.
2. **The laptop relay process** — BLE/WiFi transport, handshake, time sync, reliability, backpressure,
   sensor-frame → sensor-window assembly.
3. **The Ultra96 client** — line-delimited JSON, request/response correlation, and (dev/remote-access
   only) SSH tunnel management — see §8.
4. **The Central Game Engine** — authoritative state, combat rules, cooldowns, HP, match phase.
5. **The WebSocket server** — TLS, serving both Unity visualizers and Player 2's relay.
6. **The entire mock layer** — a simulator for every interface you own, so the other three subsystems can
   develop without hardware and you can develop without them.
7. **Latency instrumentation** — the timestamps that produce the end-to-end numbers §3.6.3 and §5.5.1 of
   the report promise to measure.

You do **not** own: IMU filtering/fusion (firmware), the classifiers (AI), avatar rendering or AR
tracking (visualizer). You own the boundaries between all of them.

## 2. Processes and how they are deployed

Three distinct processes: two symmetric `relay` instances (one per laptop) and one `engine`, all of which
run on the shared Ultra96 board alongside the classifiers. This is not a free architectural choice — the
venue WiFi enforces client isolation between personal devices, so a laptop cannot open a direct
connection to another laptop or to a phone visualizer. Only whitelisted devices can be reached by
everyone else on that network, and the Ultra96 is provisioned as one. Putting `engine` there means every
other device (both laptops, both phones) only ever needs a direct connection to the Ultra96.

```
Laptop P1                                Laptop P2
┌──────────────────────────┐             ┌──────────────────────────┐
│ relay  (player 1)        │             │ relay  (player 2)        │
│   BLE ← FireBeetle P1    │             │   BLE ← FireBeetle P2    │
│   TCP → ultra96:8888 ────┼──venue WiFi │   TCP → ultra96:8888 ────┼──venue WiFi
│   WSS → engine ──────────┼──venue WiFi │   WSS → engine ──────────┼──venue WiFi
└──────────────────────────┘             └──────────────────────────┘
                    │                                    │
                    ▼                                    ▼
          ┌────────────────────────────────────────────────────┐
          │ Ultra96 (shared)                                    │
          │   classifier service :8888  ← relay(1), relay(2)    │
          │   engine  (WSS server :8443)                        │
          │     ← /relay/1, /relay/2, /visualizer/1, /visualizer/2
          │     authoritative state                             │
          └────────────────────────────────────────────────────┘
```

Same `relay` binary on both laptops, differing only by `--player-id` and config; both are now fully
symmetric (neither hosts the engine). The engine is addressed as a network service (`wss://<host>:8443`)
by both relays identically. At match time `<host>` is the Ultra96's address on the venue WiFi, reached
directly with no tunnel; during development it can instead point at an SSH-tunnelled `localhost` port
(§8) while the Ultra96 sits on the NUS SoC Research Subnet. Either way it's a config change, not a code
change.

## 4. Wire protocol (FireBeetle ↔ Laptop) — normative

This section is the source for `shared/protocol/wire_protocol.md` and `shared/protocol/cg_protocol.h`.
**All multi-byte integers are little-endian** (both ends are little-endian; no byte swapping anywhere).

### 4.1 Frame layout

| Offset | Field | Size | Value |
|---|---|---|---|
| 0 | `MAGIC` | 1 | `0xC9` |
| 1 | `VERSION` | 1 | protocol version, currently `1` |
| 2 | `TYPE` | 1 | bit 7 = `MORE_FRAGMENTS`; bits 6–0 = packet type |
| 3 | `SEQ` | 2 | `uint16`, per-device **per-direction**, wraps at 65535 |
| 5 | `PLAYER_ID` | 1 | `1` or `2` (`0` = unassigned, only valid in `HELLO`) |
| 6 | `LEN` | 2 | `uint16`, byte length of `PAYLOAD` |
| 8 | `PAYLOAD` | `LEN` | ciphertext ‖ 16-byte GCM tag (see §4.5) |
| 8+`LEN` | `CRC16` | 2 | CRC-16/CCITT-FALSE over bytes `[0, 8+LEN)` |

Fixed overhead: 10 bytes + 16-byte auth tag = 26 bytes per packet.

`MORE_FRAGMENTS` lives in the high bit of `TYPE` rather than a new field, so the packet table in the
report stays accurate. Packet type values are therefore constrained to `0x00–0x7F`.

### 4.2 Packet types

```c
#define CG_PKT_HELLO            0x01   // device → laptop   reliable
#define CG_PKT_HELLO_ACK        0x02   // laptop → device   reliable
#define CG_PKT_TIME_SYNC_REQ    0x03   // device → laptop   reliable
#define CG_PKT_TIME_SYNC_RESP   0x04   // laptop → device   reliable
#define CG_PKT_SENSOR_FRAME     0x10   // device → laptop   best-effort
#define CG_PKT_RFID_EVENT       0x11   // device → laptop   reliable
#define CG_PKT_HEARTBEAT        0x20   // both              best-effort
#define CG_PKT_ACK              0x21   // both              never acked itself
#define CG_PKT_COMBAT_FEEDBACK  0x30   // laptop → device   reliable
```

### 4.3 Payloads (plaintext, before encryption)

All laptop-side timestamps are `uint32` milliseconds since `serverEpochUnixMs`, which the laptop sends
once in `HELLO_ACK`. Device timestamps are `uint32` milliseconds on the device's own clock.

```
HELLO                (16 B)  deviceMac[6] | playerId u8 | protocolVersion u8 |
                             firmwareVersion u16 | deviceNonce u32 | reserved u16
HELLO_ACK            (16 B)  sessionId u32 | serverEpochUnixMs_lo u32 | serverEpochUnixMs_hi u32 |
                             deviceNonce u32 (echoed)          ← echo proves freshness
TIME_SYNC_REQ         (4 B)  t0 u32                            (device clock, at send)
TIME_SYNC_RESP       (12 B)  t0 u32 (echoed) | t1 u32 | t2 u32 (laptop clock, rx and tx)
SENSOR_FRAME         (42 B)  deviceTimestampMs u32 | flags u8 | weaponId u8 |
                             dominant[6] i16 | offhand[6] i16 | torso[6] i16
RFID_EVENT           (12 B)  deviceTimestampMs u32 | weaponId u8 | reserved u8 | tagUid[6]
HEARTBEAT            (12 B)  deviceTimestampMs u32 | vbatBelt_mV u16 | vbatDom_mV u16 |
                             vbatOff_mV u16 | statusFlags u16
ACK                   (2 B)  ackedSeq u16
COMBAT_FEEDBACK       (6 B)  feedbackCode u8 | intensityPct u8 | durationMs u16 | repeatCount u16
```

`SENSOR_FRAME.flags`: bit0 `DOM_STALE`, bit1 `OFF_STALE`, bit2 `MOTION_ACTIVE`, bit3 `LOW_BATTERY`,
bit4 `CALIBRATING`, bits 5–7 reserved. `DOM_STALE`/`OFF_STALE` mean that wrist's ESP-NOW frame did not
arrive this interval and the values are the last-known repeat — the windower must know this so it does
not feed a stalled signal to the classifier as if it were fresh.

**IMU fixed-point scaling** **[config]** (`shared/config/sensors.yaml`), matching MPU-6050 full-scale
settings: accelerometer `1 LSB = 1/2048 g` (±16 g), gyroscope `1 LSB = 1/16.4 °/s` (±2000 °/s).
Comms converts to float only when building `SENSOR_WINDOW`.

### 4.4 Sequence numbers and replay

`SEQ` is 16-bit on the wire but both sides maintain a **32-bit extended sequence** (`extSeq`). On
receive, detect wrap with signed 16-bit delta: `delta = int16(new_seq - last_seq)`; if `delta > 0`, advance;
if `delta < 0` it is a reorder or replay. Increment the high half when `new_seq < last_seq` and
`delta > 0`.

Maintain a 64-entry sliding replay window per direction. Reject any packet whose `extSeq` is at or below
the window floor, or already seen. Log rejections — a sudden burst means either a bug or an attack, and
you want to be able to tell which during the demo.

### 4.5 Encryption

AES-128-GCM, pre-shared 16-byte key **[config]**, loaded from `CG_PSK_HEX` (env) or a file outside the
repo. Never commit the key; `scripts/gen_psk.py` generates one and prints the hex for pasting into
firmware config.

- **Plaintext:** the payload struct from §4.3.
- **AAD:** the 8-byte plaintext header, exactly as it appears on the wire. This authenticates
  `TYPE`/`SEQ`/`LEN`/`PLAYER_ID` — an attacker cannot renumber or retype a packet.
- **Nonce (12 B), derived, never transmitted:**
  `sessionId u32 ‖ playerId u8 ‖ direction u8 ‖ extSeq u32 ‖ 0x0000`
  where `direction` is `0` for device→laptop and `1` for laptop→device.
- **Wire payload:** `ciphertext ‖ tag[16]`, so `LEN = plaintext_len + 16`.

**Handshake packets are the one exception, and getting this wrong is a real break.** `HELLO` and
`HELLO_ACK` have no session yet. If they simply used `sessionId = 0`, then every `HELLO` ever sent would
derive the nonce `(0, playerId, 0, extSeq=0, 0)` — identical across both devices whenever `playerId` is
still `0` (which §4.1 permits in `HELLO`), and identical to a device's own previous `HELLO` after any
reboot or reconnect. Repeating a `(key, nonce)` pair under GCM leaks the XOR of the two plaintexts and
lets an attacker forge packets. It must not happen.

Therefore, for `HELLO` and `HELLO_ACK` only:

- The 4-byte random `deviceNonce` is carried **in the clear**, as the first 4 bytes of `PAYLOAD`,
  ahead of the ciphertext: `PAYLOAD = deviceNonce(u32) ‖ ciphertext ‖ tag[16]`, so
  `LEN = 4 + plaintext_len + 16`.
- **AAD** for these two packet types is the 8-byte header **‖ the 4 cleartext `deviceNonce` bytes**, so
  the cleartext prefix is authenticated and cannot be swapped.
- The nonce substitutes `deviceNonce` for `sessionId`:
  `deviceNonce(u32) ‖ playerId(u8) ‖ direction(u8) ‖ extSeq(u32) ‖ 0x0000`.
  `HELLO_ACK` derives its nonce from the *same* `deviceNonce` with `direction = 1`, so the two never
  collide with each other or with any prior handshake.
- `deviceNonce` must come from a real entropy source on the ESP32 (`esp_random()`), **not** from an
  uptime counter or a PRNG seeded at boot — two devices powering up together would otherwise draw the
  same value.
- The laptop's chosen `sessionId` must likewise be random, not a counter, so that a laptop restart
  cannot reissue a live session's ID.

Replay protection is unchanged and layers on top: the laptop rejects a `HELLO` bearing a `deviceNonce`
it has seen in the last 60 s **[config]**, and the device rejects a `HELLO_ACK` whose echoed
`deviceNonce` does not match what it just sent.

> **Note on CRC16 + GCM.** The GCM tag already provides integrity, so the CRC is strictly redundant
> cryptographically. Keep it anyway — it is specified in the report, costs almost nothing, and lets the
> receiver discard a corrupted frame before spending a decrypt on it, which matters on the ESP32 side.
> Verify CRC first, then decrypt.

### 4.6 Fragmentation

Negotiate the BLE ATT MTU up at connection time (`bleak` exposes this); target ≥ 247 bytes, giving
~244 usable. A `SENSOR_FRAME` packet is 68 bytes, so fragmentation should never trigger in practice —
but implement it, because "should never" is not "cannot", and a silently truncated packet during the
demo is far worse than dead code.

**Do not implement reassembly in Week 5.** Reserve the bit, and make the receiver treat a set
`MORE_FRAGMENTS` as a hard error: log it loudly and drop the packet. That is ~10 lines and it turns the
impossible case into a visible one. Building full reassembly now is 150 lines of code that, by the
reasoning above, can never execute — and untested code that never runs is worse than no code.

Add reassembly only if MTU negotiation is observed to fail on real hardware in Week 8. The design, if
that day comes: all fragments carry the same `TYPE` (bit 7 set on every fragment but the last) and
consecutive `SEQ`; fragment the **plaintext** into chunks, encrypt each chunk independently under its own
`extSeq`-derived nonce, and reassemble plaintexts, so every fragment is independently authenticated.
Abandon a partial reassembly after 200 ms **[config]**.

### 4.7 Golden vectors — the firmware handshake that saves a week

Create `shared/protocol/golden_vectors.json`: for each packet type, a fixed PSK, sessionId, seq, and
plaintext payload, plus the exact expected 68-byte (etc.) hex output.

`comms/tests/test_golden_vectors.py` asserts the Python codec reproduces them.
`firmware/test/test_golden_vectors.cpp` asserts the C codec reproduces them.

Both sides then provably agree before a FireBeetle and a laptop are ever in the same room. Write these
in Week 4 alongside the header. This is the highest-leverage half-day in the whole plan.

## 5. Handshake and time synchronisation

### 5.1 Sequence

```
device → laptop   HELLO            {mac, playerId, protoVer, fwVer, deviceNonce}
laptop → device   HELLO_ACK        {sessionId, serverEpochUnixMs, deviceNonce echo}
device → laptop   TIME_SYNC_REQ    {t0}                       ×N, see below
laptop → device   TIME_SYNC_RESP   {t0, t1, t2}
                  ── streaming begins ──
device → laptop   SENSOR_FRAME @ 50 Hz, RFID_EVENT on change, HEARTBEAT @ 1 Hz
laptop → device   COMBAT_FEEDBACK on event, HEARTBEAT @ 1 Hz
```

Reject `HELLO` if `protocolVersion != shared/protocol/VERSION` — respond with a `HELLO_ACK` carrying
`sessionId = 0` meaning refusal, and log loudly. A silent version mismatch is the classic integration-day
time sink.

### 5.2 Offset estimation

Standard NTP four-timestamp form, with `t3` recorded by the device on arrival:

```
offset = ((t1 - t0) + (t2 - t3)) / 2
rtt    =  (t3 - t0) - (t2 - t1)
```

**Run this 8 times at 100 ms spacing** during handshake, not once. Discard any sample whose `rtt` exceeds
the median `rtt` × 2 (BLE connection intervals produce occasional large outliers that would poison a
single-shot estimate). Take the offset from the sample with the *lowest* `rtt` — that is the least
asymmetric one, and it is a better estimator than the mean.

Re-run a single-sample sync every 30 s **[config]** and feed it into an EWMA (`α = 0.1`) so slow
crystal drift is tracked. Log the offset trend; if it moves more than a few ms per minute the parry
window will misbehave and you want to know before the demo, not during it.

### 5.3 Who applies the offset

The report says the FireBeetle computes the offset. Have it do so and stamp frames in engine time —
**but have the laptop maintain its own independent estimate and normalise on ingest anyway.** The laptop
is the side that must be right, it has the better clock, and it is the side you can debug. If the two
estimates diverge by more than 20 ms **[config]**, log a warning and trust the laptop's.

Everything downstream of relay ingest is in engine time. No other subsystem does clock arithmetic.

## 6. Reliability

| Packet | Delivery | Rationale |
|---|---|---|
| `SENSOR_FRAME`, `HEARTBEAT` | best-effort | 50 Hz stream; a dropped frame shortens a window slightly |
| `HELLO`, `HELLO_ACK`, `TIME_SYNC_*`, `RFID_EVENT`, `COMBAT_FEEDBACK` | ACK + retransmit | state-changing; a lost weapon change desyncs the whole match |
| `ACK` | never acked | obviously |

**Retransmit:** timeout `200 ms` base, exponential backoff ×2, max 5 attempts, jitter ±20% **[config]**.
After the final attempt, raise a `LinkDegraded` event rather than failing silently.

**Heartbeat:** 1 Hz each way **[config]**. Liveness timeout = 3× interval, and any inbound packet —
not just `HEARTBEAT` — counts as a sign of life.

The liveness clock starts when **streaming** begins, not when the session object is created. The
handshake carries no heartbeats and the 8-sample time-sync burst of §5.2 takes ~800 ms, so a watchdog
whose clock started at session construction is already past its timeout on its very first poll and
tears down every link the instant it becomes usable. Reset the last-seen timestamp at the
handshake → streaming transition, then start the watchdog.

On timeout: mark the link
stale, emit `MATCH_STATE {phase: PAUSED, reason: LINK_LOST, playerId}` to both visualizers, suspend
combat resolution *for that player only*, and begin reconnection with backoff (`1 s, 2 s, 4 s, … cap 10 s`).
On reconnect, redo the full handshake including time sync — the device may have rebooted and its clock
restarted.

**Backpressure:** every inbound queue is bounded and drops **oldest** on overflow.

| Queue | Depth | On overflow |
|---|---|---|
| raw packet ingest | 256 | drop oldest, count |
| sensor frame → windower | 100 (= 2 s at 50 Hz) | drop oldest, count |
| window → Ultra96 | 4 | drop oldest, count — never let inference latency compound |
| engine event queues | 512 | drop oldest, count, and **log loudly** (should never happen) |

Export the drop counters in the heartbeat log line. A rising sensor-frame drop count is the earliest
warning that the pipeline is falling behind, and it is invisible unless you count it.

## 7. Windowing (SENSOR_FRAME 50 Hz → SENSOR_WINDOW 10 Hz)

Two independent ring buffers per player — dominant wrist and off-hand — each `windowSamples` long.

**[config]** `windowSamples: 40` (800 ms at 50 Hz), `strideFrames: 5` (emit every 100 ms → 10 Hz,
87.5% overlap).

On each `SENSOR_FRAME`: append both wrists' samples, increment a counter, and when
`counter % strideFrames == 0` emit a `SENSOR_WINDOW` if the buffer is full.

**Do not emit if** more than `maxStalePct: 20` **[config]** of the samples in the window were flagged
`DOM_STALE`/`OFF_STALE`, or if the window's time span deviates from `windowSamples / 50 Hz` by more than
15% (indicating dropped frames). Emitting a window that is really a stalled signal produces a confident
wrong classification, which is worse than no classification at all.

The `weapon` field of the window comes from the last confirmed `RFID_EVENT` for that player. If no weapon
has been confirmed yet, do not send windows at all — the Ultra96 has no model to select.

## 8. Ultra96 client

**Match-time default: no tunnel.** At the venue, the Ultra96 is provisioned as a whitelisted device
directly on the match WiFi, so `relay/ultra96.py` connects with a plain TCP socket to the Ultra96's LAN
address — no SSH tunnel in the match path. `Ultra96Config.tunnel_enabled` defaults to `False` for exactly
this reason; a dev config opts back in.

**Tunnel (development / remote access only).** `relay/tunnel.py` supervises an SSH subprocess for coding,
deploying, and debugging the Ultra96 while it sits on the NUS SoC Research Subnet off-site:

```bash
ssh -J <SoC-UNIX-ID>@stfjump.comp.nus.edu.sg -N \
    -o ServerAliveInterval=5 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes \
    -L 127.0.0.1:8888:127.0.0.1:8888 xilinx@<host-id>
```

Start it, poll `127.0.0.1:8888` until connectable (max 30 s), restart on exit with backoff. Make it
skippable via `--no-tunnel` for the case where someone already has one open in a terminal, and make the
whole Ultra96 client swappable for `mock/ultra96_sim.py` via config. **Assume the tunnel will drop at
least once during a long dev session** — SoC's VPN is not reliable enough to assume otherwise, and a
supervised subprocess turns that from a lost session into a two-second stall. Because this path is no
longer in the match itself, a drop here no longer risks a demo.

**Protocol.** Line-delimited JSON (`\n`-terminated, UTF-8), one TCP connection held open for the match.
Requests are `SENSOR_WINDOW`, responses are `ACTION_RESULT`.

Add a `requestId` (monotonic `uint32`) to both, echoed by the server. The report's schema omits it;
without it you cannot correlate a response to its request when one is dropped, and you cannot measure
per-request latency — which §5.5.1 requires. **Raise this with Himeth in Week 4** so the AI-side server
echoes it.

Timeout `120 ms` **[config]** per request. On timeout, drop the request and count it; do not retry — a
stale classification is worthless because a newer window already exists. Cap in-flight requests at 2.

Discard any `ACTION_RESULT` whose `actionConfidence < minConfidence: 0.6` **[config]** at the relay,
before it reaches the engine — except `IDLE`, which always passes through since it is what clears the
avatar's animation state.

## 9. Application message schemas

Every message: `{ "type", "version", "timestamp", ... }` where `timestamp` is engine-time int64 ms and
`version` is `shared/protocol/VERSION`. Unknown `version` → log and drop.

```jsonc
// relay → engine
{ "type":"ACTION", "version":1, "timestamp":0, "playerId":1, "weapon":"SWORD",
  "action":"HORIZONTAL_SWING", "actionConfidence":0.94,
  "guardState":"IDLE", "guardConfidence":0.88 }

{ "type":"WEAPON_CHANGED", "version":1, "timestamp":0, "playerId":1, "weapon":"SPEAR" }

// visualizer → engine
{ "type":"POSITION", "version":1, "timestamp":0, "playerId":2, "x":1.2, "y":0.4, "heading":87.5 }

// engine → both visualizers
{ "type":"COMBAT_EVENT", "version":1, "timestamp":0, "attackerId":1, "defenderId":2,
  "weapon":"SWORD", "action":"HORIZONTAL_SWING", "outcome":"BLOCK",
  "damage":3, "attackerHp":40, "defenderHp":37, "rangeM":1.4 }

{ "type":"MATCH_STATE", "version":1, "timestamp":0, "phase":"IN_PROGRESS",
  "hp":{"1":40,"2":37}, "winnerId":null, "reason":null }

{ "type":"COOLDOWN_STATE", "version":1, "timestamp":0, "playerId":1,
  "cooldowns":[{"action":"HORIZONTAL_SWING","remainingMs":420,"totalMs":800}] }

// engine → relay → FireBeetle
{ "type":"COMBAT_FEEDBACK", "version":1, "timestamp":0, "playerId":2,
  "code":"HIT_TAKEN", "intensityPct":90, "durationMs":180, "repeatCount":1 }
```

`ACTION` also carries `guardState`, because `ACTION_RESULT` from the Ultra96 carries both classifier
outputs in one payload (report §4.5). The engine treats the guard field as a *continuous state update*
and the action field as a *discrete event* — they are the same message but not the same kind of thing,
and conflating them is the easiest way to break parry timing.

**Position is echoed, not just consumed.** The engine forwards each player's `POSITION` to the *other*
player's visualizer. The visualizer needs the opponent's position to place the avatar, and it must be the
engine's copy so both clients agree.

## 10. Game Engine

### 10.1 State

```python
@dataclass
class PlayerState:
    player_id: int
    weapon: Weapon | None = None
    hp: int = 100                       # [config] match.yaml
    position: Vec2 | None = None
    heading_deg: float = 0.0
    position_ts: int = 0
    guard_state: GuardState = GuardState.IDLE
    guard_entered_ts: int = 0           # engine ms when IDLE → GUARDING
    last_action: ActionClass = ActionClass.IDLE
    cooldowns: dict[ActionClass, int] = field(default_factory=dict)   # action → expiry ts
    link_ok: bool = False

@dataclass
class MatchState:
    phase: MatchPhase = MatchPhase.WAITING   # WAITING | ALIGNING | IN_PROGRESS | PAUSED | ENDED
    players: dict[int, PlayerState]
    winner_id: int | None = None
    started_ts: int = 0
```

**One coroutine writes this. No locks anywhere.** Everything else reads via immutable snapshots produced
by the writer. This is the entire justification for the single-event-loop design in report §4.7 — do not
undermine it by handing a mutable reference to the broadcaster.

### 10.2 The reorder buffer — do not skip this

Events arrive in *arrival* order but must be processed in *engine-time* order, or the ±150 ms parry
window is decided by network jitter rather than by what the players did. P1's action can easily reach the
engine before P2's earlier guard, because P1's relay is on the same machine and P2's crosses the LAN.

Hold every inbound event in a min-heap keyed on `timestamp` and release it only once
`now_engine - timestamp > reorderDelayMs` **[config]**, default `60`. This costs 60 ms of latency and
buys correct cross-player timing. Drop anything arriving more than `lateDropMs: 500` **[config]** behind
the release watermark, and count it.

Tune `reorderDelayMs` from measured cross-player arrival skew in Week 11, not by guessing.

### 10.3 Combat resolution

`resolver.py` must be a **pure function** — `(MatchState snapshot, ActionEvent, RulesConfig) → Decision`.
No I/O, no clock reads, no queue access. Every branch below then becomes a two-line unit test, and
`tests/test_resolver.py` can cover the whole rule set without spinning up a single socket. This is the
one place where discipline about purity pays for itself many times over.

```
resolve(state, ev) -> Decision:
  1. phase != IN_PROGRESS                         -> IGNORED
  2. ev.action == IDLE                            -> STATE_ONLY   (update last_action, no event)
  3. attacker.weapon is None                      -> IGNORED
  4. ev.action not in rules.moves[weapon]         -> IGNORED  (classifier/weapon mismatch — log!)
  5. ev.confidence < rules.min_confidence         -> IGNORED
  6. cooldowns[ev.action] > ev.timestamp          -> ON_COOLDOWN  (no COMBAT_EVENT; report §4.7)
  7. either position is None,
     or age(position) > positionMaxAgeMs (1000)   -> IGNORED  (cannot adjudicate fairly — log)
  8. range = |attacker.pos - defender.pos|
     range > rules.range[weapon][action]          -> MISS
  9. defender not facing attacker within
     rules.guard_arc_deg (120) of heading         -> HIT (full damage; you cannot block behind you)
 10. defender.guard_state == GUARDING and
     0 <= (ev.timestamp - defender.guard_entered_ts)
        <= rules.parry_window_ms (150)            -> PARRY  (0 damage, attacker staggered:
                                                             all attacker cooldowns +stagger_ms)
 11. defender.guard_state == GUARDING             -> BLOCK  (damage x rules.block_multiplier 0.25,
                                                             rounded up)
 12. otherwise                                     -> HIT   (full damage)
```

Then, outside the pure function: apply damage, clamp HP at 0, start the attacker's cooldown for that
action, and emit `COMBAT_EVENT` + `MATCH_STATE` + `COOLDOWN_STATE` + two `COMBAT_FEEDBACK` messages
(`HIT_LANDED` to the attacker's wrist, `HIT_TAKEN`/`BLOCKED`/`PARRIED` to the defender's). If HP reaches
0, transition to `ENDED` and set `winner_id`.

Note that step 10 fires only when the guard *began* within the parry window of the attack — a defender
who has been holding guard for two seconds gets a BLOCK, not a PARRY. Parry is a timing reward. That
distinction is what makes it a mechanic rather than a synonym.

**The comparison in step 10 is one-sided on purpose.** Use `0 <= (attack_ts - guard_entered_ts) <=
parry_window_ms`, *not* `abs(...) <= parry_window_ms`. A two-sided window lets a defender raise their
guard up to 150 ms *after* the attack and still parry it, which is both physically wrong and trivially
exploitable once a player notices. The reorder buffer (§10.2) exists precisely so that the timestamps
being compared here are trustworthy; do not then throw that away with an `abs()`.

### 10.4 Rules data

`shared/config/weapons.yaml`, owned jointly with whoever tunes game feel:

```yaml
weapons:
  SWORD:
    moves:
      HORIZONTAL_SWING: { damage: 10, range_m: 1.5, cooldown_ms: 800 }
      VERTICAL_SWING:   { damage: 12, range_m: 1.4, cooldown_ms: 900 }
      DIAGONAL_SWING:   { damage: 11, range_m: 1.5, cooldown_ms: 850 }
      THRUST:           { damage:  8, range_m: 1.8, cooldown_ms: 600 }
      CHARGED_ATTACK:   { damage: 25, range_m: 1.6, cooldown_ms: 3000 }
  SPEAR:
    moves:
      THRUST:           { damage: 12, range_m: 2.5, cooldown_ms: 700 }
      CHARGED_THRUST:   { damage: 28, range_m: 2.8, cooldown_ms: 3200 }
      SWING:            { damage:  8, range_m: 2.0, cooldown_ms: 1000 }
  MACE:
    moves:
      VERTICAL_SWING:   { damage: 16, range_m: 1.3, cooldown_ms: 1200 }
      DIAGONAL_SWING:   { damage: 15, range_m: 1.3, cooldown_ms: 1150 }
      CHARGED_ATTACK:   { damage: 32, range_m: 1.4, cooldown_ms: 3500 }
```

`shared/config/match.yaml`: `starting_hp: 100`, `parry_window_ms: 150`, `block_multiplier: 0.25`,
`stagger_ms: 500`, `guard_arc_deg: 120`, `min_confidence: 0.6`, `position_max_age_ms: 1000`,
`reorder_delay_ms: 60`.

The move sets must exactly match §5.2.2 of the report and the animation states in §6.4.2. If they drift,
the visualizer receives an action it has no animation for. Generate the visualizer's animation-state

### 10.5 WebSocket server

`wss://0.0.0.0:8443` **[config]**, TLS with a self-signed cert generated by `scripts/gen_certs.sh`.

Path-routed connections:

| Path | Client | Sends | Receives |
|---|---|---|---|
| `/relay/1`, `/relay/2` | relay processes | `ACTION`, `WEAPON_CHANGED`, link status | `COMBAT_FEEDBACK` |
| `/visualizer/1`, `/visualizer/2` | Unity clients | `POSITION`, `READY` | everything else |

Auth: a shared bearer token in the `Authorization` header **[config]**. Trivial, but it stops another
group's client on the same venue WiFi from connecting to your engine — which is a real hazard on demo
day, not a theoretical one.

Registry maps path → connection. On duplicate connect for the same path, close the old one (a phone that
crashed and relaunched should reclaim its slot, not be locked out).

**iOS caveat that will cost you an afternoon if you skip it:** the self-signed certificate requires an
App Transport Security exception plus the Local Network permission in the Unity build, per report §6.1.3.
Without them the WebSocket fails *silently*. Confirm with Jiaming in Week 5, before it becomes an
integration blocker in Week 9.

**Broadcast:** fan out with `asyncio.gather(*(conn.send(payload) for conn in conns))`, serialising the
JSON **once** and reusing the string. A slow client must never block a fast one: give each connection its
own bounded send queue (depth 32, drop oldest) and a dedicated writer task.

**On visualizer connect:** immediately send a full state snapshot — `MATCH_STATE`, both `POSITION`s,
both `WEAPON_CHANGED`, both `COOLDOWN_STATE`. A client that reconnects mid-match must not have to wait
for the next event to know what is going on.

## 11. Mock layer

This is a deliverable for the whole team, not a testing convenience. Build it in Week 5.

**`firebeetle_sim.py`** — the important one. It emits **real binary packets** through the real codec over
`loopback` or `tcp` transport, performing the real handshake and time sync with a deliberately offset and
drifting fake clock. It therefore exercises framing, CRC, crypto, sequencing, replay detection, and
reliability — everything except the BLE radio itself. Flags: `--drop-rate`, `--dup-rate`,
`--reorder-rate`, `--latency-ms`, `--clock-drift-ppm`, `--scenario <file>`. When BLE integration goes
wrong in Week 8 you will know it is the radio and not your stack, because your stack is already proven.

**`ultra96_sim.py`** — listens on `:8888`, speaks line-delimited JSON, returns `ACTION_RESULT` with
configurable `--latency-ms` (model realistic FPGA inference plus tunnel RTT) and `--accuracy` (return a
wrong class some fraction of the time — the engine must behave sanely when the classifier is wrong,
and it will be). Drives actions from the scenario file so the duel is reproducible.

**`visualizer_sim.py`** — a WSS client that publishes `POSITION` along a scripted path and asserts on
inbound messages. Doubles as the acceptance test for the engine and as a reference implementation for
Jiaming: when the Unity client misbehaves, run this against the same engine to establish which side is
wrong.

**`scenario.py`** — YAML timelines driving all three simulators from one clock:

```yaml
name: parry_then_counter
duration_ms: 6000
events:
  - { at: 0,    player: 1, weapon: SWORD }
  - { at: 0,    player: 2, weapon: MACE }
  - { at: 500,  player: 1, move_to: [0.0, 0.0] }
  - { at: 500,  player: 2, move_to: [1.2, 0.0] }
  - { at: 1000, player: 2, guard: GUARDING }
  - { at: 1080, player: 1, action: HORIZONTAL_SWING }   # 80ms after guard → PARRY
  - { at: 1600, player: 2, action: VERTICAL_SWING }     # counter while P1 staggered
expect:
  - { at: ~1080, combat_event: { outcome: PARRY,  defenderId: 2 } }
  - { at: ~1600, combat_event: { outcome: HIT,    defenderId: 1 } }
```

Each scenario doubles as a regression test and as a scripted demo you can run without hardware — useful
if a wearable fails during the Week 7 or Week 10 checks.

`scripts/run_mock_stack.sh` starts engine + two relays + two Ultra96 sims + two visualizer sims from one
command. **Target: this runs green by the end of Week 5**, before any hardware exists.

## 13. Testing

- **Unit** — CRC, header pack/unpack, payload structs, nonce derivation, sequence wrap, replay window,
  fragmentation, time-sync outlier rejection, windowing edge cases, cooldown expiry.
- **Property (hypothesis)** — `decode(encode(p)) == p` for arbitrary valid packets; any single-bit flip
  is caught by CRC or GCM; the framer resyncs from arbitrary garbage without deadlocking.
- **Golden vectors** — shared byte-for-byte with firmware (§4.7).
- **Resolver** — one test per branch of §10.3, plus boundary cases: parry at exactly 150 ms, range at
  exactly the weapon limit, cooldown expiring exactly at the action timestamp, simultaneous mutual hits,
  HP crossing 0 from a block, an action arriving after `ENDED`.
- **Integration** — full stack over loopback with lossy/reordering transport, asserting scenario
  expectations.
- **Soak** — 15-minute mock match; assert no unbounded queue growth, no memory growth, no clock drift
  beyond tolerance. Run this before every integration checkpoint.

Target ≥ 85% coverage on `protocol/` and `engine/resolver.py`. Coverage elsewhere matters less; those two
are where a bug is both most likely and most expensive.

## 16. Building before the other subsystems exist

This subsystem is deliberately built first, against simulators, while firmware / AI / visualizer are still
being written. Their real interfaces will differ from what is assumed here. That is expected and planned
for — the goal is that adapting costs a handful of file edits, not a rewrite.

### 16.1 Publish the contract before writing the code

Land `shared/` (enums, schemas, `cg_protocol.h`, `wire_protocol.md`, golden vectors) and walk the team
through it **before** they begin their Week 5 implementation. Three people conforming to one written spec
is far cheaper than one person retrofitting three improvised interfaces — and Comms is the hub, so the
adaptation cost belongs on the spoke side. A contract published late is a contract nobody follows.

### 16.2 What can and cannot be invalidated

Stable regardless of what anyone else builds — roughly 70% of the code, and it should never need
revisiting: `protocol/` (CRC, header, crypto, codec, framing, fragmentation), `transport/`, reliability,
heartbeat, backpressure, timesync, engine state, cooldowns, reorder buffer, `ws_server`, broadcaster, the
whole `mock/` layer, and `tools/`.

Expected to change once the other subsystems land — keep churn confined to exactly these:

| File | Changed by | Likely change |
|---|---|---|
| `protocol/payloads.py` | firmware | `SENSOR_FRAME` field layout, scaling, whether the torso IMU exists |
| `relay/ultra96.py` | AI | `requestId`, connection model, probability vector instead of a single class |
| `shared/config/weapons.yaml` | AI | **most likely of all** — the final class set is whatever the dataset supports, not what the report lists |
| `messages/models.py` | visualizer | fields the avatar/HUD actually need; coordinate frame conventions |
| `windowing.py` **[config]** | AI | `windowSamples` is dictated by the trained model's input shape |

### 16.3 Rules that keep the change surgical

1. **No weapon name, action name, or field offset outside the five files above.** The resolver looks moves
   up in `weapons.yaml`; it never branches on a literal. A `if weapon == "SWORD"` anywhere in `engine/`
   converts an AI class-set change from a YAML edit into a code hunt.
2. **Declare payload layouts as data, not code.** One table of `(field, type, scale)` per packet type,
   consumed by a generic packer — not hand-written `struct.pack` calls scattered across the module. A
   firmware layout change then edits one table and regenerates the golden vectors.
3. **Parse `ACTION_RESULT` behind an adapter** that tolerates both a single class and a probability
   vector, and ignores unknown keys. Do not let raw Ultra96 JSON reach the engine.
4. **Bump `shared/protocol/VERSION` on any breaking change** and let the receiver drop unknown versions
   loudly. Two subsystems disagreeing on a schema should fail with a log line, not with a plausible
   wrong number.
5. **Regenerate, never hand-edit** anything under `shared/generated/`.

### 16.4 Adapting later, safely

When a real interface arrives, the sequence is: update the contract in `shared/` → regenerate → update the
matching simulator in `mock/` to emit the *new* shape → run the test suite → fix what breaks. Updating the
simulator first means the existing tests immediately tell you the true blast radius, before any production
code is touched.

**The test suite is the anchor.** A later implementation pass — likely a fresh session with no memory of
why any of this is shaped the way it is — will otherwise happily rewrite working code it does not
recognise as deliberate. If `tests/test_resolver.py`, `test_golden_vectors.py`, and `test_crypto.py` still
pass after an adaptation, the change was surgical. **If a pass proposes deleting or weakening tests to make
them pass, that is the signal to stop and look at what it actually changed.**

### 16.5 Code conventions

The structure above is deliberately more modular than a 13-week project strictly needs, because the
module boundaries are what make §16.2's change list cheap. That is not a licence to over-build *within*
a module. Inside the boundaries, write the smallest thing that works.

- **Type hints everywhere**, `mypy --strict` on `protocol/` and `engine/`. These are the two places where
  a type error becomes a wrong number on the wire rather than a crash.
- **No abstraction with one implementation.** The transport ABC earns its keep because there are three
  transports. Do not add an ABC, factory, or registry anywhere else "for extensibility" — there is no
  Week 14.
- **Functions do one thing and fit on a screen.** If `resolve()` grows past its twelve branches, the
  extra logic belongs in `rules.py`, not in a longer resolver.
- **`resolver.py` stays pure.** No clock reads, no I/O, no logging, no queue access. Everything it needs
  arrives as an argument. This is non-negotiable — it is the only reason its test file can cover the
  whole rule set without a socket.
- **Errors:** a malformed packet is a counted, logged drop, never an exception that reaches the event
  loop. Reserve exceptions for programmer error. Every `except` names a specific exception type; a bare
  `except Exception` in an asyncio task swallows the bug that would have told you what was wrong.
- **No comments that restate the code.** Comment the *why* — why the lowest-RTT time-sync sample is
  chosen, why the nonce includes a direction byte, why the reorder buffer exists. Those are the things
  a reader cannot recover from the source.
- **Config, not constants.** Anything in the `[config]` markers above is read from YAML at startup and
  appears in the log line at boot, so a demo-day tweak never needs a code edit.
- **Delete dead code.** If the WiFi fallback transport is never exercised by Week 10, delete it and say
  so in the report rather than shipping an untested path.

### 16.6 Build in the §14 order, not all at once

Resist generating the whole tree in one shot. Build to the Week 5a–6c checkpoints and get
`run_mock_stack.sh` green early. A working mock stack is the instrument that detects an interface mismatch
the day a teammate's real component appears — without it, the mismatch surfaces during integration week
instead, which is the expensive place to find it.
