# CG4002 Group 23 — Repository Plan

Monorepo for all four subsystems. This document defines the layout, ownership boundaries, shared
contracts, and conventions. Section 4 (Communications) has its own detailed build plan in
[`COMMS_IMPLEMENTATION_PLAN.md`](COMMS_IMPLEMENTATION_PLAN.md).

---

## 1. Why a monorepo

The four subsystems use four unrelated toolchains (Arduino/ESP-IDF C++, Python + Vitis HLS, Unity C#,
Python asyncio). They cannot share a build system. What they *must* share is the **message contract** —
the binary wire format and the JSON schemas. Splitting into four repos means the contract gets copied
four times and drifts within a fortnight. One repo, one `shared/` directory, four independent build
trees underneath it.

Each subsystem directory is self-contained: you can `cd firmware/` and work without touching anything
else. Nothing outside `shared/` is imported across subsystem boundaries.

## 3. Ownership and the rule that keeps it working

| Directory | Owner | Backup | Anyone else may… |
|---|---|---|---|
| `firmware/` | Xin Hui | Himeth | read only |
| `ai/` | Himeth | Xin Hui | read only |
| `visualizer/` | Jiaming | Xian Hui | read only |
| `comms/` | Xian Hui | Jiaming | read only |
| `shared/` | **nobody alone** | — | propose via PR, needs 2 approvals |
| `design_report/`, `docs/` | all | — | edit their own section |

**The rule:** a change inside your own directory needs no review. A change inside `shared/` needs a PR
that at least one other affected owner approves, because it breaks somebody else's build by definition.
This is the whole reason the monorepo is worth it — `shared/` changes become visible instead of silent.

The repo is not yet initialised. Set it up as:

```bash

git init -b main
git config user.name  "<your name>"       # LOCAL, not --global — you have multiple accounts on this PC
git config user.email "<your NUS email>"

```

> Scope `user.name`/`user.email` to this repository, never `--global`. There is more than one Git identity
> configured on this machine and a global setting will attribute commits to the wrong account.

- **Branches:** `main` is always demo-able. Work on `comms/<topic>`, `fw/<topic>`, `ai/<topic>`,
  `viz/<topic>`. Merge to `main` via PR.
- **Tags:** `week7-individual-demo`, `week10-integration-check`, `week13-final` — so you can always go
  back to a state that demonstrably worked.
- **Commits:** `comms: add AES-GCM nonce derivation`, `shared: bump protocol VERSION to 2`.
- **Never commit:** `.env`, `secrets/`, PSK material, `*.pem` private keys, raw dataset CSVs, Vitis/Vivado
  build directories, Unity `Library/` `Temp/` `Logs/` `Build/`, `__pycache__`, `.venv`.
- **Git LFS** for `*.bit`, `*.hwh`, `*.fbx`, `*.onnx`, `*.h5`, and Unity texture/audio binaries.

Add a `.gitignore` before the first commit — Unity's `Library/` is several GB and is extremely
unpleasant to remove from history afterwards.

## 5. The contract-first workflow

This is the single most important process decision, and it is what makes the Week 7 individual demos
and the Week 8–9 integrations actually land.

**Week 4–5: freeze `shared/` before anyone writes subsystem code.**

The contract is small — roughly eight JSON schemas, one C header, one enums file. It can be written in a
day. Once it exists:

- Firmware writes packets against `cg_protocol.h` and tests them against a Python decoder, with no laptop
  software finished.
- AI writes `classifier_server.py` against `sensor_window.schema.json` and can be driven by a replay
  script, with no FireBeetle finished.
- Visualizer builds its entire UI against `MockDataInjector` feeding schema-valid JSON, with no backend
  finished.
- Comms builds the relay and engine against `mock/firebeetle_sim.py` and `mock/ultra96_sim.py`, with no
  hardware at all.

Every subsystem gets to Week 7 independently demo-able. Integration in Weeks 8–9 then becomes "swap the
simulator for the real thing", one link at a time, rather than four unfinished things meeting for the
first time.

**Rule:** every one of the four subsystems must have a working mock counterpart for every interface it
owns. Comms owns the most interfaces, so Comms writes the most simulators — that is why `comms/mock/`
is a first-class deliverable and not a testing afterthought.

## 6. Integration order (maps to Sections 7 weeks 8–10)

Bring links up one at a time, each with the *other* side still simulated. Never connect two
newly-written things at once.

| Step | Link made real | Other side still mocked | Week |
|---|---|---|---|
| 1 | Wrist ESP32-C3 → belt FireBeetle (ESP-NOW) | laptop = serial logger | 8 |
| 2 | FireBeetle → laptop relay (BLE) | Ultra96 = `ultra96_sim.py`, engine = real | 8 |
| 3 | Laptop relay → Ultra96 (SSH tunnel) | FireBeetle = `firebeetle_sim.py` | 8 |
| 4 | Engine → Unity visualizer (WSS) | everything upstream = `scenario.py` replay | 9 |
| 5 | Visualizer → engine (POSITION) | one phone real, one phone simulated | 9 |
| 6 | Two players, full chain | nothing mocked | 10 |

Keep every simulator working after its link goes real. When something breaks at Week 12 you diagnose by
swapping one real component back out for its simulator until the failure disappears. That is worth far
more than the hour it costs to maintain them.

## 7. Cross-cutting conventions

- **Timestamps** are `int64` milliseconds. Every app-layer message carries `timestamp` already normalized
  to the Game Engine clock. Comms does the normalization on ingest; no other subsystem does clock maths.
- **Player IDs** are `1` and `2`. Never `0`, never strings — `0` is reserved as "unset" in the binary header.
- **Every app-layer JSON message** carries `{ "type", "version", "timestamp", "playerId" }` plus its own
  fields. `version` is `shared/protocol/VERSION`. A receiver that sees a version it does not know logs
  and drops rather than guessing.
- **Enum values on the wire are UPPER_SNAKE strings** in JSON (`"HORIZONTAL_SWING"`) and `uint8` in the
  binary protocol. `enums.yaml` defines both mappings; the codegen emits both.
- **Logging:** structured, one JSON object per line, to `logs/<component>-<timestamp>.jsonl`. Every match
  is logged in full. This is what lets you produce the latency numbers Section 3.6.3 and 5.5.1 promise,
  and lets you replay a failed demo run afterwards.
- **Config over constants.** Anything a tester might want to tune (parry window, cooldowns, HP, ranges,
  window length, heartbeat interval) lives in `shared/config/*.yaml`, not in source.
